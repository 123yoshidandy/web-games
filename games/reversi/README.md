# リバーシ

8×8 の盤で、黒と白の石をはさんで返す2人のボードゲーム。ブラウザで遊べる（スマホの縦持ち向け、PC でも遊べる）。

- CPU と対戦（やさしい・ふつう・つよい・とてもつよい）
- 2人で1台を使って対戦
- 待った（1手戻す）、続きから
- ホーム画面に追加すると、オフラインでも遊べる（PWA）

絵（盤・石・アイコン）はすべて自作の SVG。

## 遊び方

### ルール

世界オセロ連盟（WOF）の公式ルール（英語版 https://www.worldothello.org/about/about-othello/othello-rules/official-rules/english ）で確かめた。日本オセロ連盟のルールのページ（https://www.othello.org/lesson/lesson/rule.html ）は、一部しか読めなかった（読めた範囲には、触れたマスに打たなければならない、など盤の上の作法の決まりがあり、画面のゲームには関係しない）。

- 盤は 8×8。最初に中央の4マスに石を置く。白が d4・e5、黒が e4・d5（列 a〜h は左から、行 1〜8 は上から。黒が右上と左下）。公式のルールでは図でしか示されていないので、標準の配置に合わせた
- 黒が先手。交互に1つずつ置く
- 相手の石を、縦・横・斜めの8方向のどれかで、自分の石ではさめるマスにだけ置ける。はさんだ石はすべて自分の色に返す。返った石が別の石をはさんでも、それは返らない（連鎖しない）
- 置けるマスがあれば、必ず置く（パスはできない）。置けるマスがないときだけパスになり、相手の番になる
- 両者とも置けなくなったら終わり。石の多い方が勝ち。同じ数なら引き分け

### 公式のルールと違う点・決めた点

- **パスは自動。** パスは操作にせず、置けない人の番は自動で飛ばし、「白はパス」のように短く知らせる
- **空きを残して終わったとき。** WOF の公式ルールには、空きマスをどちらかに数える決まりはない（大会によっては勝った人に数える扱いがあるが、確かめられていない）。どちらでも勝ち負けは変わらないので、画面は盤の上の石の数をそのまま出し、空きの数を添える
- **石の数の上限。** 実物は各自 32 枚。画面では手持ちの数を数えず、上限を設けない
- **待った。** 公式のルールにはない。ローカルの対戦だけで使える（オンライン対戦の定義には入れていない）
- **時間の決まり（持ち時間）は入れていない。**

### 操作

- 置けるマスが、金の輪と手番の色の点で光る。押すと置く
- 置いた石は上から落ち、返る石は置いた石に近い順に裏返る。CPU の手も同じ動きで見せる
- 最後に置いた石に、赤い点が付く
- 上のバー：左がホーム、右が待ったと遊び方。盤の上に黒と白の石の数を出し、手番の側を金の枠で囲む
- **待った**：CPU 戦では、あなたの直前の手と、そのあとの CPU の手をまとめて戻す。2人で対戦するときは1手ずつ戻す。終わったあとでも戻せる
- **続きから**：手を打つたびに記録を保存する。タイトル画面の「続きから」で再開する。決着したら消す
- CPU 戦では、あなたの石（黒・先手か、白・後手か）を選べる

## CPU

CPU は自分の席のビュー（盤と手番。リバーシに隠す情報はない）だけを見て決める（`public/js/cpu-player.js`）。ゲームに乱数はなく、CPU の判断にも使わない。同じ点の手は、ビューから作った別の乱数で選ぶので、同じ局面なら同じ手になる。

読みは `public/js/engine.js`：

- **中盤**：アルファベータ法（ネガマックス）。局面の点は、マスの重み（角は大きく、角の隣は小さく。角が埋まったら隣の減点を消す）と、着手可能数（置けるマスの数）の差
- **終盤**：残りの空きが決めた数以下なら、最後まで読み切って石の差で決める（相手の置けるマスが少なくなる手から試す）
- 読む量は、深さと局面の数（node の上限）で打ち切る。時間では打ち切らない（端末の速さで手が変わらないように。テストで再現できるように）。上限に届いた読みは捨て、前の深さの答えを使う

| 強さ | 中盤の読み | 終盤の読み切り |
|---|---|---|
| やさしい | 2手（相手の石を全部返す手と、全部返される手は分かる）。点に大きな迷いを足す | なし |
| ふつう | 3手 | 残り8マスから |
| つよい | 必ず4手。局面の数が6万に届くまで1手ずつ深く（7手まで） | 残り12マスから |
| とてもつよい | 必ず6手。局面の数が20万に届くまで1手ずつ深く（9手まで） | 残り14マスから（局面の数が35万を超えたら読み切りをあきらめ、中盤の読みに切り替える。そこまでに読んだ局面も中盤の上限に数える） |

### 勝率

`node scripts/cpu-match.mjs <試合数> <強さA> <強さB>` で測った。同じ強さの CPU は同じ局面で同じ手を打つので、最初の4手をシード付きの乱数で打ってから CPU に任せ、試合ごとに席（黒・白）を入れ替えた。

| 対戦 | 試合数 | 勝率 | 引き分け | 石の差（平均） |
|---|---|---|---|---|
| ふつう 対 やさしい | 400 | 94.5% 対 5.5% | 0% | +34.4 |
| つよい 対 ふつう | 200 | 96.5% 対 3.5% | 0% | +37.4 |
| とてもつよい 対 つよい | 200 | 68.0% 対 30.0% | 2.0% | +12.0 |

どの組み合わせでも、止まった試合はない。席（黒・白）による偏りは、強さに差がある組では小さい（黒 49.5〜51.5%）。とてもつよい 対 つよいは、黒 43.0%・白 55.0% だった（200試合の揺れはおよそ ±3.5 ポイント）。

### 1手の時間

開発用の Mac（Apple M2 Pro、Node 22）で測った。スマホでは、この数倍（およそ3倍と見込む）かかる。とてもつよいの最長が、スマホで1秒ほどに収まるように、局面の上限を決めた。

- 中盤の上限は、25万では序盤の最長が 376ms だったので、20万に下げた
- 終盤の読み切りの上限は、70万では、読み切れずに中盤の読みに切り替えた局面で 90万局面・602ms かかった（ほかのセッションの計測と並行で、重い状態）。35万に下げ、読み切りで読んだ局面を中盤の上限に数えるようにして、最長 253ms にした（残り14マスの30局面のうち22で読み切る）

局面の段階ごと（8試合、空きの数で分けた）：

| 空き | つよい 平均／最長 | とてもつよい 平均／最長 |
|---|---|---|
| 60〜40 | 66ms／83ms | 244ms／281ms |
| 39〜25 | 45ms／68ms | 175ms／217ms |
| 24〜15 | 14ms／47ms | 79ms／148ms |
| 14〜10（読み切り） | 3ms／15ms | 13ms／117ms |
| 9〜0 | 0.1ms／1ms | 0.1ms／1ms |

とてもつよいの最長は約 0.28 秒で、スマホでは約 0.85 秒の見込み。つよいは約 0.25 秒。やさしい・ふつうは 3ms 以下。

対戦の計測（`cpu-match.mjs`）でも1手の時間を出す。上の勝率の計測は、ほかのセッションの重い計測と並行で回したので、時間は長めに出た（とてもつよい：平均 179ms・99% 566ms・最長 798ms、つよい：最長 238ms）。

CPU は、前の手で石が返る動きが見えるように、0.7秒おいてから考え始める。

## オンライン対戦

netplay-kit の「サーバーがゲームを進める型」。2人で、足りない席は CPU で埋められる。オンラインでは「一手戻す」も使わない。対戦中に部屋を出た人の席は CPU が引き継ぐ。オンラインではヒントを出さない。

- 手元で遊ぶ：web-games の直下で `npm run dev:online`（全ゲームのテスト用サーバー。ws://localhost:8787）を起動し、`public/` を localhost で開いて「オンラインで遊ぶ」
- 入口とロビーの画面は、netplay-kit の `netplay-lobby.js`（`public/js/netplay/` の写し。ここでは直さない）
- 接続先は `public/js/online-config.js`。`DEPLOYED_SERVER_URL` が空のあいだは、公開したページで「オンラインで遊ぶ」を出さない（web-games のサーバーをデプロイしたら書く）
- サーバーの入口は `server/src/handler.js`（`createHandler(定義, { keyPrefix: 'reversi' })`。web-games の1つのスタックから `?game=reversi` で呼ばれる）
- テストは `test/online.test.js`（test-kit の `testOnline` で、部屋の作成・開始・終局まで・再接続・退出を確かめる）

## 開発

素の HTML / CSS / JavaScript（ES Modules）。ビルドはない。

```bash
npm install
npm test                                   # Vitest
python3 -m http.server 8080 --directory public   # http://localhost:8080/
node scripts/cpu-match.mjs 200 strong normal     # CPU どうしの勝率
```

GitHub Pages では、リポジトリのルートの `index.html` が `public/` へ移動する。

### ファイル

| ファイル | 役割 |
|---|---|
| `public/js/rules.js` | 盤・最初の配置・はさんで返す・置けるマス・石の数（DOM に依存しない） |
| `public/js/game.js` | 進行（手番・パス・終わり・勝敗）。操作は `applyCommand` だけで受け、記録から `Game.replay` で再現する。断る操作は状態を変えない |
| `public/js/game-view.js` | 席ごとのビュー（盤・石の数・手番の人の置けるマス） |
| `public/js/engine.js` | CPU の読み（縁つきの 10×10 の盤、アルファベータ法、終盤の読み切り） |
| `public/js/cpu-player.js` | CPU の強さと、ビューから手を決める処理 |
| `public/js/game-controller.js` | ローカルの対戦（CPU 戦・2人で1台）。待った、保存と続きから、CPU を間を置いて打たせる |
| `public/js/ui.js`・`art.js` | 画面と絵 |
| `public/sw.js`・`manifest.webmanifest` | PWA（自分のファイルはネットワークを先に、字体はキャッシュを先に使う） |
| `server/src/game-definition.js` | オンライン対戦の「ゲームの定義」（netplay-kit の形） |
| `server/src/handler.js`・`public/js/online-config.js`・`public/js/netplay/` | オンライン対戦のサーバーの入口・接続先・netplay-kit の写し |
| `scripts/cpu-match.mjs` | CPU どうしの対戦と勝率・1手の時間 |

### テスト

- `rules.test.js`：マスの名前、最初の配置の向き、最初の置けるマス、8方向をまとめて返す、はさめない列は返さない、盤の端で回り込まない、連鎖しない
- `game.test.js`：黒が先手、断る操作で状態が変わらない（ランダムな操作を大量に送る）、パス、終わり（石がなくなる・盤が埋まる）、引き分け、ランダムな試合の終わり方、記録からの再現
- `cpu-player.test.js`：CPU どうしの試合が止まらない、ふつうがやさしいに・つよいがふつうに勝ち越す、どの強さも即勝ちの手を選び即負けの手を避ける、終盤の読み切りが枝刈りなしで最後まで読んだ結果と一致する（パスをはさむ形も）、ビューだけで決める、局面の数で打ち切る
- `game-controller.test.js`：CPU が人の番で止まる、白を選ぶと CPU が先に打つ、待った（CPU 戦・2人・終わったあと）、続きから
- `game-definition.test.js`：オンライン対戦の定義（受け付け・断る・再現・CPU の代行）とビュー
- `pwa.test.js`・`offline.test.js`：PWA のファイルとアイコン、オフラインでの起動（service worker をキャッシュとネットワークを差し替えて動かす）
